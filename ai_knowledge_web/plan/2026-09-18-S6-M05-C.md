## 3. 开工内容

### 3.1 P0 修复（无 `T-xxx`）—— 让流"真的在流"

#### 步 1 · 把编排搬出请求线程（治 `#174`）

**改 `ai_knowledge_web/src/main/java/com/knowledge/ai/controller/ChatController.java:90-107`**

现在是（**这就是缺陷本身**）：

```java
SseEmitter emitter = new SseEmitter(SSE_TIMEOUT_MILLIS);
EmitterSink sink = new EmitterSink(emitter);
try { chatStreamService.chat(user, request, sink); }   // ← 同步跑完
catch (...) { ... } finally { sink.complete(); }
return emitter;                                        // ← 才返回 ⇒ Spring 才 initialize
```

改为**先返回 emitter，编排交给工作线程**：

1. 注入新执行器（步 2 建）。
2. 提交任务前先把 `LoginUser` 与 `traceId` **取出来** —— 它们**都不会自己跟过线程边界**
   （`汇总.md` §5 的老坑 + `S4-E2` 的 `traceIdPropagating`）。
3. 工作线程里 `LoginUserContext.set(user)` + `TraceContext.set(traceId)`，
   **`finally` 里两个都 `clear()`** —— 池化线程不清，下一个不相干的任务会**继承**上一个的身份与 traceId，
   **那比没有更糟**（日志里会出现两个不相干的操作共用一个 id）。
4. 异常处置与 `sink.complete()` **原样搬进工作线程的 `try/finally`**（语义不变）。
5. ⚠️ **提交被拒要当场发出去**：`AbortPolicy` 下 `execute()` 会抛 `RejectedExecutionException`，
   而此时 emitter 还没 initialize ⇒ `sink.error(...)` + `sink.complete()` 会**堆进 `earlySendAttempts`**，
   initialize 时重放 —— 用户看到一条 error 事件，而不是一个挂到 5 分钟超时的空连接。
   **不处理就是"队列满 = 用户盯着空白等 5 分钟"。**

#### 步 2 · 给问答单开一个池（**不复用 `taskExecutor`**）

**改 `ai_knowledge_web/src/main/java/com/knowledge/ai/config/AsyncConfig.java`**

理由与 `retrievalExecutor` 分开时**同一条**（那边已把这套推理写死）：**背压形状不同**。

| 池 | 负载 | 队列满时的正确反应 |
|---|---|---|
| `taskExecutor` | 解析/索引，用户可等 | `CallerRunsPolicy`（反压给提交者） |
| `retrievalExecutor` | 在线关键路径 | `AbortPolicy`（尽早失败） |
| **新增 `chatExecutor`** | 在线关键路径，**且一旦开始就占用几分钟** | **`AbortPolicy`** —— 绝不能 `CallerRunsPolicy`，那会让请求线程跑完整轮问答，**等于把 `#174` 原地还原** |

- 线程名前缀 `ak-chat-` · core 4 / max 8 / 小队列 · `waitForTasksToCompleteOnShutdown(true)`。
- **`TaskDecorator` 要传播两样**（`traceId` **和** `LoginUser`）⇒ **不能直接复用** `AsyncConfig::traceIdPropagating`。
  新增 `chatContextPropagating`，把 `traceIdPropagating` 的取舍原样继承
  （提交线程没有 traceId 就**不造**，让工作线程自己生成 —— 凭空生成的 id 与任何请求都对不上）。
- 判据要能证明"身份真的跟过去了"，否则这个装饰器又是一个"写了但没做"。

#### 步 3 · 事件生命周期（`#175` 的前置）

**改 `ChatController.EmitterSink`**：补 `emitter.onTimeout(...)` / `onCompletion(...)` / `onError(...)` → `alive = false`。
现在 `alive` **只在 `send()` 抛异常时才翻**，于是"超时后编排还在发"要等到下一次 `send()` 才被发现，
而超时是 5 分钟，中间可能一次 send 都没有。

⚠️ **保留既有取舍不变**：客户端断开后**编排仍跑完**（`G5-13`「每次提问都留痕」要它）。
收尾落库照做，只是不再往连接上写。

#### 步 4 · 让身份跟过 ASYNC 续跑（治 `#175`）

**改 `ai_knowledge_web/src/main/java/com/knowledge/ai/core/security/JwtAuthFilter.java`**

```java
@Override
protected boolean shouldNotFilterAsyncDispatch() {
    return false;   // 本仓的鉴权上下文**只能**由本过滤器建立；异步续跑不给它，上下文就是空的
}
```

**为什么是这条路，而不是「把 ASYNC 移出安全链」**（`spring.security.filter.dispatcher-types: request,error`）：
后者的语义是「异步续跑不再过安全链」，短平快，但它是**在全局过滤器注册上打了个洞**。
真正的病因是 **`JwtAuthFilter` 是本仓唯一的身份来源**（`STATELESS` + 无 `SecurityContextRepository`，
没有任何仓库能在第二次 dispatch 把上下文恢复回来）—— 于是 `OncePerRequestFilter`
「一次请求只跑一次」这条默认假设，**在本仓恰好是错的**。在病因处修，别在症状处绕。

#### 🔴 一条硬约束（摸底时才发现，它决定了整条链的形状）

`PdfDocumentParser` 有**一把全局串行锁**（`LOCK`，其 javadoc 调用纪律第 3 条），
而真 VL 描述实测 **40~60 秒/张**（`#179`）。⇒ **描述绝不能发生在解析期**：

所以必须拆成两段，**这是本批最主要的结构决定**：

| 段 | 在哪 | 快慢 | 为什么必须在那一侧 |
|---|---|---|---|
| **抽图** | 解析期（**锁内**） | 快（取字节 + 算 md5 + 落 MinIO） | 字节**只**在 opendataloader 的临时产物目录里，而那个目录在 `finally` 就被删 |
| **描述** | 分片之后（**锁外**） | 慢（每张一次 VL） | 绝不能让 VL 的延迟进入那把锁 |

⚠️ **一个被我否掉的替代方案**（写下来免得后人再想一遍）：把图从临时目录拷到暂存区、

正是被这类"把工作挪到之后"咬出来的。锁内多持几秒是**明码标价的代价**，比多一套生命周期便宜。
