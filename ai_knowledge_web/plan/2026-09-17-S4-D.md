### 3.2 业务流程图

> 触发条件：跨 ≥3 个组件 ✅ · 异步任务 ✅ · 状态机 ✅ · 幂等/并发 ✅ —— **必须画**。

```mermaid
flowchart TD
  A["POST /kb/ID/reindex（mode = IMMEDIATE 或 SCHEDULED）"] --> B["ReindexService 读 kb.index_generation = g"]
  B --> C["目标代 g+1：确保分区 kbID_gNext 存在"]
  C --> D["逐文档推进（断点 = 已完成文档跳过）"]
  D --> E["每篇 doc：向量写进新代分区"]
  E --> F{"还有文档?"}
  F -- "是" --> D
  F -- "否" --> G["原子切换点：UPDATE sys_kb SET index_generation = g+1"]
  G --> H["检索侧改为只查新代分区"]
  H --> I["滚动清理：drop 第 g-N 代及更老"]
  D -. "中途 kill / 断电" .-> J["旧代分区完好未被触碰；检索照常（G3-5 通过）"]
  J -. "重启后重跑" .-> D
```

> **图里的关键点**：切代是**一次 MySQL UPDATE**，不是 Milvus 操作 —— 所以它是真原子；
> 而**旧代在切换前一个字节都没动**，这就是 `G3-5`「中途 kill 旧索引仍可用」的实现基础。

### 3.4 步 0 探针结论（**2026-09-17 实测，5/5 通过** · `MilvusPartitionProbeTest`）

> 先 `javap` 读方法面（`withPartitionName` 写入 / `withPartitionNames` 检索·查询 / 建·删·释放分区 **全在**），
> 再**真库跑数据往返** —— 方法在 ≠ 行为对，本仓库刚被 `describeIndex(fieldName)` 静默忽略咬过。

| # | 探针问的问题 | 实测结论 |
|---|---|---|
| 1 | 写进 A 分区的点，查 A 分区能查到吗 | ✅ 能（写入路由生效） |
| 2 | 查 A 分区会**漏进** B 分区的点吗 | ❌ 不会 —— **分区隔离成立**（本方案的存亡所系） |
| 3 | 不指定分区时的默认语义 | 查**全部**（含 `_default`），不是"查不到" |
| 4 | `dropPartition` 只删该分区吗 | ✅ 只删它 —— **但必须先 `releasePartitions`**（见下 ①） |
| 5 | 写进**不存在**的分区会怎样 | **显式失败**，不会隐式创建 → 实现必须 ensure-exists |
| 6 | 分区数上限够用吗 | **32 个全部建成并列出** ✅（本设计需 库数 × 保留代数 ≈ 24） |

**三条会改实现写法的发现**：

1. 🔴 **裸 `dropPartition`（不先 release）会以 `65535`(`UnexpectedError`) 失败** —— 而且**它只体现在返回值里**。
   本探针**第一版正是没检查返回值**，于是"查得到 21"被误读成"删除可见性延迟"，32 个探针分区也全泄漏在集合里。
   → **滚动清理必须 `releasePartitions` → `dropPartition` → 校验返回值**。这是本仓「拒绝按成功了处理」的又一实例，
   与 S0 的 `describeIndex` 恒真守卫、C3 的 `get_stats` 假失败是**同一族**：接口返回 Success 不代表服务端执行了。
2. 🟡 **查一个已 drop 的分区是「报错」而不是「返回空」** —— 语义上**安全**（比静默返回空集或回落到查全部都好），
   但它是检索侧的一条**硬约束**：绝不能去查一个可能不存在的分区，否则**整个检索请求会炸**而不是少几条结果。
3. 🟡 **`R#getMessage()` 在成功时 NPE**（内部 `exception` 为 `null`）—— 诊断/日志代码不能无条件调它。

**实测代价**：`release + drop` 约 **1.2s/分区**（32 个清理耗时 ~38s）。滚动清理是低频操作，可接受；
但它意味着**不能把"每篇文档重建"做成"每次建一个分区"**。

## 10. 建议

1. **下一步就是 `S4-E`**（纯优化批：`T-O01` + `T-O02` + `T-O06`，10.5 人天）—— 它已按「尽早做」的
   裁定排在 `S4-D` 之后，`S5` 开工随之后移 2 周。**不要把它再往后挪**：`T-O02` 有一条时序硬约束
   （`S5` 的评测集 `T-711` 基线必须建在修好后的管线上），而 `T-O01` 后面堵着三项。

2. **强烈建议先插一个「测试清理收敛」小批**（遗留 9，**第三次**撞上同一形状）。
   现在每加一种持久化产物（新表 → Milvus 向量 → 分区）都要人肉找齐 4+ 个清理函数，
   而**漏了的表现是"跑完看着干净、其实留下了东西"**——本批就是靠手查分区列表才发现的。

3. **`S5` 开工时把这三条一起处理**（都属检索侧，同一批做省一次联调）：
   软删库不召回 · 重建后返回新代 · `G4-8` 的运行时侧（搜 `A-100` 不命中 `A-1000`）。

4. **`O9` 的优先级建议再上调一次**：本批实测重建 300 篇文档耗时约 **2.5 分钟**
   （`13:07:58 → 13:10:15`），其中绝大部分是逐篇的嵌入调用 —— 正是 `O9` 说的"分片级 n 次调用"。
