| **终态只在「可被检索」时才叫 `READY`**（S4-B 定） | 解析完成 → `INDEXING`（**不是** `READY`）。`READY` 的语义是「唯一可被检索的状态」（《03》§4.2），而向量未入 Milvus 时标它就是本项目最怕的**「报告说成功」**。`INDEXING` 诚实地表示「解析完了，索引还没建」 | `DocRecordWriter#markParsed` javadoc · `V13` 头注释 · `S4-M05-B` §8 判据 18 |

| **「无文本层」的密度判据只在 `pages >= 2` 时生效**（S4-B 定） | 扫描件的形状是「**页数多** + 每页几乎没字」，不是「单页文档本来就短」。单页文档只判**绝对零**（`chars == 0`）。**误报比漏报更伤**：漏报顶多是老问题，误报会把用户引向一个无从下手的动作（S4-B 的 W1'） | `TextLayerGuard` 类注释 + 两条用例 · `S4-M05-B` §8.1 |
| **`chars` 的口径 = 「可检索的文本量」**（S4-B 定） | 含正文 + 标题 + **表格单元格**，不含图片/页眉/页脚。**表格必须计入** —— XLSX 整篇就是一张表，漏掉它就等于说「这张表不存在」（S4-B 的 W2'：111 行 × 9 列被判「1 页仅 12 字符」） | `TikaDocumentParser#text` + `PdfDocumentParser#fromJson` 的累计点注释 |

| **依赖冲突先查「谁声明的版本」再决定修法**（S4-B 定） | 拉齐 S0 的 `opendataloader 1.11 → 2.5`：`NoSuchMethodError` 且来自**传递依赖**时，优先在 `dependencyManagement` **锁到功能方自己声明的版本**，而不是给传递方加 `exclusion`（后者会在对方真用到该类时变成 `NoClassDefFoundError` 静默埋雷）。**注释必须写明为何不能靠「就近取胜」** | `pom.xml` 的 `dependencyManagement` · `S4-M05-B` §5 |
| **Milvus 写入路径不 flush**（S4-C3 定） | growing segment **不 flush 也可被 `query`/`search` 看到**（STRONG 一致性读己之写）；flush 只影响持久化与 compaction，而它有**速率限制（10 秒一次）**—— 每次写入后 flush 会让每篇文档白等一个窗口（实测用例 68s → 6.7s） | `S4-M05-C3` §6+7 订正段 · `MilvusChunkWriter` 类 javadoc |
| **判「向量写进去了没有」用 `entities/query` 的 `count(*)`，不用 `get_stats` 的 `rowCount`**（S4-C3 定） | 后者**只统计已 flush 的数据** —— 写入路径不 flush 之后它会给出"没写进去"的**假失败**（实测 `rowCount=0` 而同刻实查 81 条）。`READY` 的语义是"**可被检索**"，不是"已持久化" | `S4-M05-C3` §6+7 订正段 · 速览 §5 |
| **Milvus 分区四条口径**（S4-D 定 · **2026-09-17 由 `S4-D2` 从速览 §5 正式提升到这里**） | ① **写进不存在的分区会显式失败**（不会隐式创建）→ 写之前必须 `ensure`（`MilvusChunkWriter#replaceDocument` 已自带）；② **drop 分区必须先 release** —— 裸 `dropPartition` 报 `partition cannot be dropped, partition is loaded, please release it first`（**Java SDK 只给 65535，REST 会把话说清楚**），顺序固定 **release → drop → 校验返回值**；③ **查一个不存在的分区是「报错」而不是「返回空」** → 检索侧绝不能指向可能不存在的分区，否则**整个检索请求会炸**而不是少几条结果；④ **`R#getMessage()` 在成功时 NPE**（内部 `exception` 为 null）→ 诊断/日志代码不能无条件调它 | `S4-D` §9 · 速览 §5 |
| **持久化产物必须登记，且由机器检查漏项**（S4-D2 定 · **下批起照此办理**） | 「新增 X 就要同步改 N 处」的约定，**光靠注释提醒一定会漏**（本项目「新增持久化产物、清理函数不认识它」已复现**三次**：`sys_chunk` 表 → Milvus 向量 → 按代分区）。做法：**登记表**（新增产物只加一行）+ **覆盖率闸**（枚举 `information_schema` 里带 `kb_id`/`doc_id`/`user_id` 的表，凡未登记且未显式豁免 → **抛错点名**）+ **残留自检用独立观测点**（不看清理命令的返回值）。样例：`ai_knowledge_app/scripts/lib/probe-teardown.mjs`。⚠️ 闸必须放在**建探针之前**，放 `finally` 里会「闸抛错 → 清理不执行」，等于用防残留的闸制造残留 | `S4-D2` §8 额外取证 · 该文件模块头注 |
| **清存量 ≠ 修根因**（S4-D2 定） | 只要还有**别的入口在造**，存量清零就只是快照（实测：清掉 3629 行孤儿登录日志 → `mvn test` 一轮又添 **91 行**）。报「已清干净」时必须同时说清**还有哪个入口在造**，否则那句话下次开工就是假的 | `S4-D2` §8 判据 9 · §3 #99 |
| **根因靠数据定，不靠「谁最可疑」定**（S4-D2 定） | `S4-D2` 开工时的根因假设（`purgeProbeUsers` 漏删登录日志）**被数据推翻** —— 真漏点在**后端 `@SpringBootTest` 用例**，而被怀疑的那个脚本里该前缀**一行都没有**。若照假设动手，会花 1.5 人天修一个从没漏过的地方，真漏点继续漏。**先查数据（备份 + 按前缀分组计数），再定根因** | `S4-D2` §8 末节 · §3.4 假设 5 |
