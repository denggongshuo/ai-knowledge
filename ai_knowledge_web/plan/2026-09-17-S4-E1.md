### 3.2 业务流程图

> 触发条件：① 跨 ≥3 个组件 **满足**（请求线程 / 任务表 / 解析池 / MinIO / Milvus）·
> ② 涉及异步任务与事务边界 **满足** · ③ 有状态机 **满足** · ④ 有并发/幂等 **满足**。

```mermaid
flowchart TD
  A["请求线程 POST /kb/{kbId}/doc/upload<br/>@Transactional + @AuditLog"] --> B["建 sys_document 行<br/>终态 UPLOADED"]
  B --> C["提交上传任务（既有 taskExecutor）<br/>仅做：接收文件 + 转存 MinIO + markStored"]
  C --> D["enqueueParse(docId, kbId)<br/>写 sys_async_task：type=doc-parse, status=PENDING"]
  D --> E[("sys_async_task<br/>PENDING / RUNNING / DONE / FAILED<br/>+ kb_id + doc_id + attempt + next_retry_at")]

  F["ParseWorker 轮询<br/>（专用有界池，与 taskExecutor 隔离）"] --> G{"领取：for update skip locked<br/>status=PENDING 且 next_retry_at 到点"}
  E -.-> G
  G -- "领到" --> H{"按 kbId 的配额<br/>有空位?"}
  H -- "否" --> H1["放回 PENDING<br/>（不占线程，下次再领）"]
  H -- "是" --> I["RUNNING + locked_by/locked_at"]
  I --> J["Future.get(timeout)"]
  J --> K["DocParseService#parseDocument<br/>解析 → 体检 → 清洗 → 分片 → 增强 → 向量化"]
  J -- "超时" --> L["cancel(true) → FAILED<br/>「解析超时（超过 N 分钟）…」"]
  K --> M{"结果"}
  M -- "ParseException / BizException<br/>（文档自身的问题）" --> N["FAILED · 直接终态<br/>不重试 —— 重试也还是这个文件"]
  M -- "基础设施异常" --> O{"attempt < 3 ?"}
  O -- "是" --> P["退避重试<br/>next_retry_at = now + backoff"]
  O -- "否" --> Q["死信：FAILED + 告警日志"]
  M -- "成功" --> R["DONE<br/>文档 INDEXING / READY"]
  P --> E
  L --> S["GET /doc/tasks/{taskId}<br/>**重启后仍可查**（内存未命中回落 DB）"]
  N --> S
  Q --> S
  R --> S
```

## 5. 依赖与工具决策

**默认不引**。

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **不引依赖（既有栈）** | 表驱动 + `select ... for update skip locked` 领取（`O1:53` 的既定方案）· 专用 `ThreadPoolExecutor` · `ReentrantLock.tryLock(timeout)` · `CompletableFuture.get(timeout)` —— 全是 JDK 与既有依赖 | 无 | ✅ **采纳** |
| 候选 A：Redis Stream（Valkey 8.1 已在栈里） | `XADD`/`XREADGROUP` 消费组 | 多一套「消息」语义要维护；且**任务态仍要落 MySQL**（`GET /doc/tasks/{taskId}` 要重启可查）→ 等于**两处状态**要同步，正是最该避免的形态 | ❌ |
| 候选 B：`@Scheduled` + 线程池（不起独立 consumer 线程） | 更少代码 | 调度器只有 2 个线程（`AsyncConfig.taskScheduler`），且要承载回收站清理等既有职责；解析领取代际会与之争抢 | ❌ |
| 候选 C：引入 MQ（Kafka/RabbitMQ） | 真正的异步解耦 | `O1:60` 已论证：这个规模用不到，运维成本与「任务态要查得到」的需求不匹配 | ❌ |

**推荐**：**不引依赖** · **理由**：本批要解决的是「调度语义缺失」，而表驱动 + `skip locked` 在 MySQL 上是成熟范式，
且**天然持久化** —— 恰好一次满足 `O1` 判据 4（重启不丢）与判据 6（重启后可查），不需要第二处状态。
