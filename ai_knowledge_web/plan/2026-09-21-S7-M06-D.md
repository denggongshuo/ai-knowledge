## 5. 依赖与工具决策

**默认不引。**

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **不引依赖（既有栈）** | 版本模型 = `sys_document` 加三列（分片/向量本就按 `doc_id` 组织，每个版本一条 doc 行是**最自然**的落点）；回滚 = 复制分片 + 既有 `ChunkVectorizer`；diff = 元数据对照（纯 SQL 投影） | 无 | ✅ **推荐** |
| 候选 A：独立 `sys_doc_version` 表 | 版本单独建表，`sys_document` 只存当前态 | 分片/向量/trace 全按 `doc_id` 索引 ⇒ 历史版本要么另建一套分片表，要么回滚时重解析；两条都比"每版本一条 doc 行"重得多 | ❌ 不引 |
| 候选 B：引 diff 库（如 `java-diff-utils`） | 后端算文本 diff | §6.8 明写 v1 不做文本 diff；引一个库只为一个"预留接口" | ❌ 不引 |

**推荐**：**无新依赖** —— 版本用 `sys_document` 加三列，回滚复用 `ChunkVectorizer`，diff 只做元数据对照。
**理由**：分片、向量、检索 trace **全部按 `doc_id`** 组织；"每个版本 = 一条 `sys_document` 行"让历史版本的分片天然独立保留，回滚只需复制分片再向量化，无需重解析、无需另一套分片存储。

> 无新依赖 ⇒ 不写「同类产品对比」。

### 8.3 全量回归第一次是红的 —— 根因是我自己的后端（判据 14 的插曲）

第一次全量：`847 / 3 红 / 2 跳过`，红的**全是本批未改动的类**（`DocParseFlowTest` 22 里红 3、
`ParseAuditTrailFlowTest` 红 1），**且每次红的成员都不一样** ⇒ 判为偶发，逐条查：

1. **现象**：`docId` 状态停在 `UPLOADED`、分片数 0、产物为 null —— 形态都是「解析作业没被领取」。
2. **锁定**：给 `claim` 加临时诊断 ⇒ **空领取与失败 1:1 对应**（run B 2↔2；run C 3↔3），
   而**漏掉的 docId 每次不同**（run B `{…322,333,335}` · run C `{…385,390,395}`）。
3. **逐条证伪（留痕）**：
   - 「库里积了陈旧 PENDING 残渣」→ **推翻**：`sys_async_task` 全程 0~2 行，跑完 0 行；`ParseWorkerFlowTest#noForeignPendingJobs` 绿。
   - 「入队未提交（worker 线程上事务没关）」→ **推翻**：19 次入队日志全部 `tx=false thread=ak-task-N`。
   - 「领取线程带着旧快照」→ **推翻**：19 次领取全部 `txBefore=false`（含 3 次空领取）。
4. **真根因**：**同一个 MySQL 上跑着第二个消费者** —— 我本机 `mvn spring-boot:run` 的后端
   （线程名 `ak-parse-*`）每秒领一次 `sys_async_task`。它在「`enqueue` 完成」与「用例 `drainOnce()`」
   之间把作业领走：`claim` 是 `for update skip locked`，行正被那个领取事务持锁 ⇒ **被跳过** ⇒ 用例领到 **0 条**；
   随后断言面对的是"别人正在解析"的文档 ⇒ 停在 `UPLOADED`。
5. **证据（两头对得上）**：
   - 后端日志里出现**正是**用例漏掉的那两个 taskId（`265704ade75297b2` = docId 999011385 ·
     `7d087a99d4034b0f` = docId 999011395），执行线程 `ak-parse-2` / `ak-parse-4`；而用例自己领到的那个 taskId 在后端日志里 **0 次**出现。
   - 独立 DB 轮询（另开一个会话）看到同一行先 `PENDING(attempt=0)` 后 `RUNNING(attempt=1)`
     —— 说明"既看得见、又锁着"，正好是"外部事务在飞行中"的样子。
6. **证伪该根因**（只改一个变量）：**关掉那个后端、其余不变** ⇒
   `DocParseFlowTest` **22/22 绿**、19 次领取 **0 次空**；再跑全量 ⇒ **`847 / 0 红`**。
7. **结论**：**不是本批引入的缺陷**，是"测试与任何同库消费者共享同一个全局作业池"的既有脆弱性 ——
   `#128`「解析作业未被领取」家族的**第三种机制**（前两种：全局最旧优先 + 陈旧 PENDING 残渣，
   见 `plan/2026-09-17-测试可靠性.md` §9-1）。现有守卫 `noForeignPendingJobs` **查不出它**：
   它查"库里有没有别人的行"，而这次库里干净、只是有别人**在领**。

### D-② 🔴 Milvus 有 **236 条无主向量**，且**没有任何清扫能发现它** ⇒ 判据 16「Milvus = 0」**未满足**
