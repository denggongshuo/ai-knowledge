# AI Knowledge · 企业级 RAG 知识库

一个 RAG 知识库系统，覆盖文档上传到引用溯源的完整链路，外加权限与密级、模型管理、审计、
检索质量评测和运维分析。知识库常用的横向能力 —— 存储编排、鉴权与权限模型、多模型接入、
审计与可观测 —— 都已就位，可以直接当知识库脚手架的起点用，也可以作为 RAG 落地的参考实现。

后端 `Spring Boot 4.0` / `Java 25` / `Spring AI 2.0.1` · 前端 `Vue 3 + TypeScript` ·
约 **12.6 万行**（后端 Java 10.0 万 / 前端 2.5 万）· **155** 个测试类 · Gitee 开源

---

## 功能概览

两条主链路：

- **入库**：上传（分片、秒传、断点续传）→ 入库防护与病毒扫描 → 路由 → 视觉理解 → 清洗 →
  分片 → 向量化 → 索引增强（文档级摘要 + HyQ）
- **检索问答**：混合检索（向量 + BM25）→ RRF 融合 → 重排 → 上下文组装 → SSE 流式生成 →
  引用解析与原文定位

横向：RBAC、数据范围、知识库授权三层求交（过滤在检索前完成）、密级贯通、append-only 审计、
多模型注册与切换、未命中闭环、检索链路全量打点、健康自检，以及 Docker Compose 一键起依赖。

测试与评测也是这套东西的一部分：155 个测试类守着关键约束，其中包含"把配置改坏后判据必须
转红"这类反向用例；检索侧有一份可复现的评测（24 题、分题型 `Recall@5`、带负向锚、`nprobe`
三档），结果见下文。

> 种子数据里有演示账号（超管 `admin`）和固定短信验证码，只用于本地演示库。
> 部署前请更换全部默认凭据与 `JWT_SECRET`。

## 快速开始

**前置**：JDK 25 · Maven 3.9+ · Node 22+ · Docker Desktop（Compose v2+）

```bash
git clone https://gitee.com/shuogehaoshuai/kb_rag.git ai-knowledge
cd ai-knowledge

# 1. 起基础设施（首次 Milvus 需要 1~2 分钟才 healthy，属正常）
docker compose up -d
docker compose ps                # 期望 mysql / minio / etcd / milvus / neo4j / valkey 均 healthy

# 2. 配置环境变量（只需一次）
cd ai_knowledge_web
cp .env.example .env
#   必填：JWT_SECRET（openssl rand -base64 48）+ MYSQL_* / NEO4J_* / MINIO_* / REDIS_*
#   可选：各类模型 API Key —— 留空也能启动，只是不能问答
#   .env 已被 gitignore，不会入库

# 3. 起后端（工作目录必须是 ai_knowledge_web，.env 按工作目录加载）
mvn spring-boot:run

# 4. 自检：五个存储必须全部连通
curl http://localhost:8080/api/health/storage
# {"code":0,"message":"success","data":{"allUp":true,"upCount":5,"total":5,...},"traceId":"..."}

# 5. 起前端
cd ../ai_knowledge_app
npm install
npm run dev                      # http://localhost:5173
```

不需要手工建表：Flyway 在应用启动时执行 `db/migration/V*.sql`（`baseline-on-migrate: true`），
在空库上自动建表并灌种子，同时建好 MinIO bucket 和 Milvus collection。

常见坑：如果看到 `Failed to parse the host:port pair '${MYSQL_HOST}:${MYSQL_PORT}'`，
是 `.env` 没被加载（工作目录不对），不用去查数据库。

```
                     └───────────────────────┬──────────────────────────────┘
                                             │  REST + SSE
┌────────────────────────────────────────────▼─────────────────────────────────────────────┐
│  接入层   TraceFilter(traceId)  →  Spring Security / JWT  →  RBAC + 数据密级 + DataScope   │
├──────────────────────────────────────────────────────────────────────────────────────────┤
│  文档入库链路  pipeline                                                                      │
│    上传 → 入库防护/病毒扫描 → 路由(routing) → 视觉理解(vision) → 清洗(cleaning)                  │
│         → 分块(chunking) → 向量化(vectorize) → 索引增强(enhance/HyQ)                          │
├──────────────────────────────────────────────────────────────────────────────────────────┤
│  检索问答链路  pipeline                                                                      │
│    查询 → 混合检索(向量 + 关键词) → RRF 融合 → [知识图谱旁路 ✓开关] → 重排 → 上下文组装              │
│         → SSE 流式生成 → 引用解析(CitationParser，角标 ↔ 原文定位)                              │
├──────────────────────────────────────────────────────────────────────────────────────────┤
│  治理横切  审计（append-only + 敏感字段脱敏）· 检索链路追踪 · 未命中闭环 · 模型用量记录 · 健康自检        │
└──────────────────────────────────────────────────────────────────────────────────────────┘
     存储：MySQL(元数据/审计) · Milvus(向量) · MinIO(对象) · Neo4j(图谱) · Valkey(缓存/限流)
```

三处实现细节，对应成本、闭环和可排查性：

| 位置 | 设计 | 说明 |
|---|---|---|
| `pipeline/enhance/HyqGate` | HyQ 假设问题生成带门控 | 不是所有查询都值得多花一次模型调用。A/B 实测省下 64% 的模型调用，评分从 `0.682` 掉到 `0.658` |
| `pipeline/retrieve/MissSink` | 未命中闭环 | 检索不到的问题落库，供运营分析定位知识空洞；补文档 → 重建 → 自动重放验证 → 标记已解决 |
| `pipeline/retrieve/RetrievalTraceWriter` | 检索链路全量打点 | 可复盘"这一问为什么召回了这些片段"。一次真实问答：`embed 107ms · rerank 1979ms · 生成 1132ms · 合计 5198ms`，Top1 相似度 `0.992687` |

## 关键设计决策

### 分片：以结构边界为主，语义切分默认关闭

切太碎丢上下文，切太粗噪声大。语义切分按 embedding 相似度找断点，同一份文档两次索引可能
切出不同结果，检索出问题就无从排查，所以没有采用。

实际用的是两级流水线：第一级锁定结构边界（标题层级路径注入，表格、代码块、完整列表作为
原子块），第二级只对超长块做递归分隔符兜底。代价是结构混乱的超长文档切分质量不如语义切分，
这是主动接受的损失。切分行为有测试守着（`headingClosesThePreviousSection`、
`paragraphsInOneSectionMergeIntoASingleBlock`）；语义切分那一侧是
`semanticSplitFailsLoudlyInsteadOfDegradingSilently` —— 配了就明确失败，不静默用递归分隔符替代。

### 混合检索 + RRF 融合，不做分数加权

纯向量检索对字面精确匹配很弱：型号、错误码、专有名词（比如 `RFC 7231`）经常召不回来。
所以向量和 BM25 双路并行召回，用 RRF（倒数排名融合）合并 —— 只取排名、不做归一化，因为
向量分和 BM25 分量纲不同，直接相加没有意义。融合权重也没做：没有评测基线之前调权重等于瞎调。
`RrfFusionTest` 覆盖，确认是 `Σ 1/(k+rank+1)` 而不是分数相加。

### 三个阈值各管一件事

最早只用一个相似度阈值，结果统计口径打架：报表说未命中，日志里明明召回了分片 —— 同一个数字
被当成两件事用。现在拆成三个：

| 阈值 | 默认值 | 作用 |
|---|---|---|
| `recallThreshold` | `0.15`（库级） | 低于它不进融合池，宽进 |
| `missThreshold` | `0.35`（全局） | 最高分低于它判未命中，严出 |
| `lowScoreWarn` | `0.65`（全局） | 低于它标黄提示，只提示不过滤 |

召回宁多勿漏，精排才是判官；而未命中是一个业务判定，不是检索判定，两者混用必然打架。
不变量 `missThreshold > recallThreshold` 写死在代码里，防止后人改坏。

### 表格：双表示 + 整表原子块 + 子块回表

PDF 里的报价单、合同条款表是检索最容易漏掉的内容：拍平成文本会丢行列语义，切碎又会丢表头。
做法是同一张表生成两份 —— Markdown 版给大模型读（生成时能还原结构），行式自然语言版
（"错误码 10021，含义 权限不足"）给向量化用；整表作为一个原子块不切；行级子块负责召回，
命中后回表取整表上下文，上限 30 行 / ±5 行。本质是检索粒度要小、给模型的上下文要全。
`TableWindowTest` / `TableLookupFlowTest` 覆盖。

### 权限：三层求交，过滤发生在检索之前

越权内容一旦进了模型上下文就晚了。三层取交集：功能权限、数据范围、知识库授权；先用 MySQL
算出可见 `doc_id` 集合，作为 Milvus 标量过滤条件传入检索。文档密级只能 ≥ 所属知识库
（可升不可降），密级同样参与标量过滤，有测试（`docSecretLevelIsTheMaxOfDocAndKb`）。
审计走独立事务提交，接口层不提供任何修改或删除入口（`noMutatingEndpoints`），从接口维度
保证 append-only。

## 一个被砍掉的功能：知识图谱旁路

动机是：向量检索的基本单位是 chunk，而多跳问题的答案藏在 chunk 之间的关系里。比如
「订单系统分库分表基于一致性哈希」+「一致性哈希由 Karger 提出」，问「订单系统的分片方案
是谁提出的」时，第二跳天然召不回来。

做法是在索引侧复用文档级摘要那一次模型调用，顺手抽出实体与关系写入 Neo4j（token 只多约
10~15%）；检索侧做实体链接 + 1~2 跳邻居扩展，与主链路 top-k 去重合并后统一进 Rerank。
整条旁路可整体开关，主链路不依赖它。

验收门槛事先写在需求里：多跳 + 聚合提升不足 `+5pp` 就关闭。

| 题型 | 图关 | 图开 | Δ |
|---|---|---|---|
| 单跳 | 100.0% | 100.0% | +0.0 |
| 多跳 | 57.1% | 57.1% | +0.0 |
| 聚合 | 75.0% | 62.5% | −12.5pp |
| 多跳 + 聚合 | 66.7% | 60.0% | −6.7pp |

不达标，所以按门槛关闭图谱旁路、降为 P2 预留（代码不删，保留开关）。

根因比结论本身有用：把召回列表打出来看，图谱确实召回了正确答案，但它进不了融合后的 top-5 ——
RRF 是等权融合，图谱这一路只贡献 1~6 条候选，而向量、BM25 各 15 条，图谱单路召回在 RRF 里的
权重天然被稀释。瓶颈在融合策略的候选数不对等，不在图谱召回本身。

## 检索质量评测

检索类项目容易只讲"用了什么技术"，讲不出效果。所以这里有一份可复现的评测：

```bash
cd ai_knowledge_web
mvn -B test -Peval -Dtest=RetrievalEvalTest
# 产物：target/eval-report.txt（逐题）· target/eval-nprobe.txt（nprobe 三档）
```

| 项 | 做法 |
|---|---|
| 评测集 | 24 题：单跳 / 多跳 / 聚合各 8 条（`src/test/resources/eval/queries.json`） |
| 金标 | 有标准答案片段，可算 `Recall@5` |
| 负向锚 | 题目要求"查 `A-100` 不得召回 `A-1000`"（`mustNotRecall`），防止靠多召回刷分 |
| 可复现性 | 连跑两次结果一致 |
| 参数扫描 | 量化 `nprobe` 三档对召回的影响 |
| 不进默认跑批 | 标注 `excludedGroups=eval`，`mvn test` 仍是"全替身、无网络"，评测要显式 `-Peval` |

实测结果：

```
SINGLE     题数= 8  Recall@5=1.000  全中率=1.000
MULTI      题数= 8  Recall@5=1.000  全中率=1.000
AGGREGATE  题数= 8  Recall@5=0.806  全中率=0.625
合计        题数=24  Recall@5=0.935
```

聚合题明显弱于单跳和多跳（`0.806` vs `1.000`）。查下来根因不是召回精度，是 top-5 名额竞争：
要数清"有几款"就得把那一组行都取回来，而每一行都在和正文块、标题块抢同样的 5 个位子。
据此明确了不做表格独立召回通道这个方向。

需要和结论一起读的边界：语料只有 3 篇合成报价单、27 个分片。它证明的是链路通、结果可复现，
不等于真实语料下的效果指标；真实规模下的基线需要重新测。这里刻意不设通过线 —— "是多少"
本身就是结论，设一条拍脑袋的线只会得到"为了让用例变绿而调阈值"的动机。

## 工程纪律

- **评测集带负向锚**。24 题里有一类要求"查 `A-100` 不得召回 `A-1000`"。没有负向约束的
  召回率很容易靠多召回刷高，负向锚是让评测不能自欺的那颗钉子。
- **增强功能先定门槛，再跑 A/B**。门槛写在需求里，避免事后找理由（图谱旁路就是这么被关掉的）。
- **对"应当有效"的配置坚持反向证伪**：把它改坏，判据必须转红；转不红就如实记录"本形态下
  测不出"，不记"通过"。比如某条 Nginx 缓冲配置做了四次受控实验，开关行为一致，记录为
  "本机无区分度"，而不是含糊地打勾。
- **评测不进默认跑批**：`mvn test` 保持"全替身、无网络"的硬口径。

## 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 后端 | Spring Boot **4.0.0** · Java **25** · Spring AI **2.0.1** · Spring MVC（命令式）+ WebClient（调模型） · JPA · Flyway | 与 Security / 事务 / JPA 这套既有生态无缝 |
| 前端 | Vue 3 · TypeScript · Vite · Element Plus · Pinia | 单页运营台，TS 保证接口契约不漂 |
| 存储 | MySQL 8.4（元数据/审计）· Milvus 2.6（向量，dim 1024 / `bge-m3`）· MinIO（对象）· Neo4j 5.26（图谱）· Valkey 8.1（缓存/限流） | 每份数据只放一个归属地，职责不重叠；Milvus 的标量过滤是把权限前置到检索的关键 |
| 安全 | Spring Security · JWT · ClamAV（病毒扫描）· 敏感字段脱敏 | 入库防护 + 审计链 |
| 可观测 | traceId 全链路（响应体 / 日志 / 审计表）· Actuator 自定义健康组件 · logback 异步不丢日志 | 一次搜索串起用户 → 请求 → 检索 → 生成 → 审计 |
| 部署 | Docker Compose（9 个服务） | 一条命令起全套依赖，降低复现门槛 |

整体是命令式技术栈（JPA、`@Transactional`、`ThreadLocal` 登录上下文、Servlet 过滤器贯穿
traceId、分片续传），只在此之上用 WebClient 非阻塞地调模型接口。全链路改响应式会牵动上述
所有基础设施，收益小于风险；相关取舍记在 `ai_knowledge_web/pom.xml` 的注释里。

## 已知限制

- 检索评测集只有 24 题、语料为合成数据，能验证链路正确与可复现，不等于生产语料下的效果指标
- 真实规模下的 `Recall@5` 未测
- Rerank 的第三方契约未做网络验证；评测时 `rerankEnabled` 为关闭状态
- 文档版本机制未实现（无版本表、无归档，`version` 字段为空）
- 未做压力测试、未做安全渗透；限流与熔断为本地实现
- 前端部分页面共用 mock 层，便于脱离后端独立调试
- 图谱旁路默认关闭（A/B 无区分度，见上文）

## 两个教训

1. **单一事实来源**。曾出现同一份文档的解析结果在三个页面显示三个数，因为各页自己写死了
   数值。修法是建立数据字典作为唯一来源，所有页面从同一处取值。示例数据必须单一来源，
   否则页面永远对不齐。
2. **自动化脚本必须幂等**。首轮批量脚本非幂等，重复执行导致报告失真。修法是先判断目标态，
   再决定改不改。
